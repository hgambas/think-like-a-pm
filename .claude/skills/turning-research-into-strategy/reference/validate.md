# validate — counting rule first, then claimed vs. audited

## Purpose

Check which claims the evidence actually supports. Write the counting rule before counting, count out of the flat inventory, and publish the difference between what was previously claimed and what the audit found.

## When to use it

Whenever a number, quote, or "the research shows" claim is about to drive a decision — a build order, a pricing move, a promise to a partner. Also whenever two live documents disagree.

## Inputs

The flat inventory from `evidence`. No inventory, no counting — offer to run `evidence` first.

## How it works

1. **Write the counting rule before counting.** Example of a real one: "a call counts for a goal only if the person described the pain in their own world — market commentary, advice, and descriptions of other people's problems do not count." Get the user's confirmation of the rule before applying it; the rule is a judgment call they own.
2. **Count only from the inventory, never from the smells section.** Anything stamped **smell** — the user's own belief, however confidently stated — contributes zero to every number here. It is not a weak vote or a half-item; it is not a vote at all. A smell becomes a number only by going and finding real sources for it, which are then inventoried and counted on their own merits. Where a claim under audit *originated* in a smell, say so in the verdict: "this was a hunch, and nothing in the corpus supports it yet" is a finding worth publishing, not an embarrassment to bury.
3. **Count**, citing item IDs. List borderline cases separately, each with its reasoning, so the counts can be re-run under a looser rule without redoing the work. If any counted item came from a source stamped **pre-grouped** at intake — a workshop board that arrived with its themes already formed — say so beside the number: "9 mentions, 6 of them from one pre-grouped board." A count that leans on somebody else's arrangement is still usable; it just has to admit it.
4. **Run a second, separate count for customer fit** — grade each source against the target-customer profile (who the product is actually for): fits / marginal / outside / not a buyer, each with a reason. This stops loud non-buyers from outweighing the actual segment. Skip only if no target-customer profile exists yet — and log that as an open question.
5. **Publish the claimed-versus-audited table**: claim, audited finding, verdict. Then a short paragraph per mismatch explaining exactly what assumption produced the inflated number — the explanation is the useful part, because it stops the same inflation from happening again.
6. **Record counter-evidence, not just support.** If a framing actively failed in three calls, that goes in the table too.
7. Route every claim that cannot be settled to the decision log: open question, or waiting on the named person who can settle it.

## A healthy run produces

A claimed-vs-audited table a skeptic could re-derive: the rule, the IDs counted in and out, the borderline register, and a plain verdict per claim. Real example of the shape: "Claimed 11 calls supported matchmaking; under the own-world rule, 3 qualify — a real signal, not a majority theme."

## Pitfalls

- **Counting first, rationalising the rule after.** The rule comes first precisely so the count can't drift toward the answer someone wants.
- **Deleting failed claims.** Downgrade in place and show the mismatch. A quietly deleted claim teaches nobody anything.
- **Auditing the user's decisions.** Decisions get logged and can be revisited through the decision log — but this command audits evidence claims, not choices.
- **Stopping at "the number was wrong."** If you haven't explained how the wrong number was produced, the audit is half done.
